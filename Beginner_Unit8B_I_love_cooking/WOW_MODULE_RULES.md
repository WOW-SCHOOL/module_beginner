# WOW SCHOOL · Обязательные правила будущих модулей

## A. Роль модуля
1. Модуль используется **после занятия с преподавателем** для самостоятельного закрепления.
2. Он не должен выглядеть как методичка для преподавателя или техническая демонстрация.
3. Весь видимый текст обращён непосредственно к ученику.
4. Тема и уровень берутся из переданного материала. Не усложнять язык без причины.
5. Модуль должен помогать повторять и закреплять, а не перегружать объяснениями.

## B. Стартовый экран
6. Использовать подход Unit 6B: крупная тема + полноценное объяснение, что ученик потренирует.
7. Всегда добавить отдельную заметку, что подсказки / правила / transcript можно открывать при необходимости.
8. На старте 3–5 понятных chips по навыкам / содержанию.
9. Стартовый экран должен быть понятным и полезным сам по себе, а не декоративным.

## C. Подсказки и поддержка
10. Подсказка, transcript и простое правило располагаются преимущественно **под визуалом слева**.
11. Помощники скрыты до клика и не загромождают правую карточку задания.
12. Transcript не должен быть обязательным для выполнения listening, это опора по желанию.
13. Подсказка не выдаёт ответ напрямую.
14. Если нужен пример, он тоже оформляется как скрытый helper и не ломает layout.

## D. Интерактив
15. Не превращать каждый блок в multiple choice.
16. Повторно использовать удачные механики можно, но не одинаковой последовательностью и не без тематической адаптации.
17. В каждом модуле минимум 2 блока должны заметно отличаться от прямых референсов.
18. В каждом модуле минимум 1 **signature interaction** — новая механика под конкретную тему.
19. Drag-and-drop всегда желательно дублировать tap-to-select / tap-to-place.
20. Анимация должна пояснять действие: соединение пары, движение времени, сборка фразы, переход по маршруту, раскрытие карточки и т. п.
21. Если есть возможность добавить лёгкую, полезную анимацию — добавлять.

## E. Audio и диалоги
22. Сохранять British English TTS (`en-GB`) из Unit 6B, если нет готового аудио.
23. Синтез речи — **железобетонно тот же по логике**, не заменять голосовую концепцию без отдельного указания.
24. Длинный текст разбивать на короткие фразы для стабильного воспроизведения.
25. Добавлять audio там, где оно помогает: vocabulary, listening, pronunciation, model sentence, dialogue.
26. Не добавлять аудио механически в каждый экран.
27. В диалогах и transcript использовать **имена людей**, а не `A / B`.
28. В озвучиваемом тексте **не произносить имя говорящего**, если это формат mini-dialogue / dialogue в стиле Unit 6B block 7.
29. В самом текстовом transcript при этом должно быть понятно, кто говорит каждую реплику.
30. Формат из Unit 6B block 7 считать эталонным для будущих dialogue/listening блоков.

## F. Layout и размеры
31. Базовый размер модуля: **1600×900**.
32. Этот размер и общую геометрию интерфейса **не менять** без отдельного задания.
33. Масштабировать весь модуль пропорционально через `fit`.
34. Правый и левый блок должны выглядеть сбалансированно и помещаться без искажений.
35. Нижний progress / `Задание X из Y` не должен исчезать из-за длинного контента.
36. Правая task-панель: вопрос, варианты, feedback, task progress. Не помещать туда длинные transcript / правила.
37. Длинные списки прокручиваются внутри своего контейнера, а не ломают экран.
38. Ни один текст, ответ, кнопка или label не может быть обрезан.
39. Использовать wrapping и при необходимости небольшое responsive-уменьшение шрифта до того, как появится overflow.
40. Никакие элементы не перекрываются и не выходят за контейнер при 1600×900.

## G. Изображения
41. Изображения не кропить: `object-fit: contain`.
42. Важные лица, руки и предметы полностью внутри кадра.
43. По умолчанию block visuals 4:3; preview 16:9; reading — желательно portrait 9:16.
44. Финальные фотографии генерируются отдельными файлами. Никаких коллажей и вырезания из общего листа.
45. Пока фото не готовы, модуль обязан иметь красивый fallback.

## H. Прогресс, переходы, results
46. Прогресс сохраняется через `localStorage`.
47. Ученик получает понятную обратную связь после каждой попытки.
48. Неправильный ответ не раскрывает правильный автоматически.
49. Переход от задания к заданию должен быть всегда понятным и единообразным.
50. Навигация и логика progress-bar должны быть едиными во всех модулях.
51. После завершения — **единый results screen**, визуально и логически одинаковый от модуля к модулю.
52. Results screen может менять только контент под тему / результат, но не общий паттерн экрана.
53. Сброс прогресса должен работать.

## I. Internal / developer
54. Скрытый dev-режим допускается для QA, но не виден обычному ученику.
55. Не показывать в UI слова `developer`, `experimental`, `QA`, `debug`, имена архивов и внутренние заметки.
56. Перед релизом удалить / заменить все template placeholders.

## J. Release
57. Обязательны iframe, oEmbed, OpenGraph preview и корректный GitHub Pages path.
58. Обязателен `ANSWER_KEY.md`.
59. Обязателен `IMAGE_PROMPTS.md` и `VISUAL_MANIFEST.json`.
60. Перед ZIP: `node -c app.js`, визуальный QA, проверка всех ответов и всех длинных состояний.

## K. Non-negotiable invariants
61. Сохранять идею welcome screen из Unit 6B.
62. Сохранять helpers под визуалом слева.
63. Сохранять British English TTS и общую логику озвучивания.
64. В диалогах использовать имена вместо `A / B`.
65. В TTS-озвучке не проговаривать имена говорящих в mini-dialogues / dialogues, если текст на экране уже маркирован именами.
66. Не менять базовое разрешение модуля и общую структуру двух колонок.
67. Финальный results screen должен быть одинаковым по паттерну.
68. Если пользователь в будущем добавляет новое “железобетонное” правило, его нужно включать в этот раздел как постоянный инвариант.
